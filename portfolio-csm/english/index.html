Blizzard Case Deep Dive

Deep DiveDelivering a hard no without losing the customer

Problem

A refund the terms ruled out

  • The ask: refund an in‑game item.
  • The terms: items apply instantly — non-refundable.
  • The trap: terms only visible via an external link.

Escalation

Three rounds, same answer, rising heat

  • Round 1: "no refund" — the customer came back angrier.
  • Round 2: "When did you ever show me the terms?"
  • Round 3: "Why design it against the customer?" — the policy answer had run out.

Answer

The best possible answer

  • Honesty: the terms hide behind a link because they're too long for the game UI.
  • Commitment: proposed an in‑purchase preview of the refund clause to the dev team.
  • Apology: for the refund itself — not for the misunderstanding.

Lessons

What I felt and learned

  • Felt: being right three times can still be a failing conversation.
  • Learned: the real question was "why wasn't I warned" — answer that one.
  • Learned: can't give what's asked? Give a reason, a fix, an apology.

ONE TICKET

Blizzard Case Deep Dive

Deep DiveHow a repeated ticket became a US HQ-approved standard

Problem

A rule that punished honest mistakes

  • The rule: refunds only within 7 days.
  • The case: paid on the wrong account, couldn't log in, window closed.
  • By the book: "reject" — correct by policy, wrong by common sense.

Judgment

Finding the structural cause

  • Shift: read the pattern, not single tickets.
  • Evidence: zero logins on the charged account — mis‑payment, not abuse.
  • Criterion: allow a late refund when the account shows no access history.

Execution

From proposal to standard

  • Documented: every recurrence — data, not anecdotes.
  • Approved: team review first, then a formal request to US HQ.
  • Adopted: now part of the standard refund procedure.

Lessons

What I felt and learned

  • Felt: the policy line and the customer's side aren't opposites.
  • Learned: documentation turns a complaint into a decision.
  • Learned: organizations move on organized evidence, not loud frustration.

Experiment

Channel and message experiment

  • Before: hiring relied heavily on standard job boards such as JobKorea and Saramin.

KPI-based value selling

  2. Package: translate pain into retention, hiring, and service KPI language.

WALKMATE

Problem Reframing

Core role: Repositioned an AI prototype around user journey value, not detection features

Role

  • Role: User Journey Reframing Lead
  • Contribution: Reframed obstacle detection into a walking guidance value story and aligned priorities, voice-first UI flow, and quality criteria.
  • Target users: visually impaired walkers and operators who need to review risk-detection evidence.

Problem

  • The first concept over-indexed on tactile paving obstacle detection and missed the full walking journey.
  • User value was clearer around destination movement, route recovery, and reduced interaction burden.
  • Without risk image, location, and detection-type records, false positives and delayed guidance would be hard to diagnose.

Hypothesis

Value message test

  • Feature angle: "AI detects obstacles on tactile paving."
  • Journey angle: "AI helps users continue the walking journey and gives operators evidence for quality review."
  • Decision: used the journey angle because it connected the product to user outcome, operator workflow, and supportability.

Loop

  1. Discover: reframe the real job-to-be-done from obstacle alerts to route confidence.
  2. Design: create a voice-first flow for risk detection, guidance, route recovery, and admin review.
  3. Measure: define guidance delay, route deviation, duplicate TTS, and detection record quality.
  4. Sell: explain the PoC as a safer journey and support loop, not just a computer-vision feature.

DeToks

AI Cost Story

Core role: Reframed an LLM tool as a business case for reducing repeated AI work

Role

  • Role: AI Cost Narrative & Core Logic Planner
  • Contribution: Reframed token optimization from a compression feature into a safe-reuse business case while defining task decomposition and cache criteria.
  • BDR relevance: practiced translating technical architecture into cost, speed, and reliability trade-offs for AI buyers.

Problem

  • LLM CLI workflows repeatedly inject the same context, increasing token use, latency, and cost.
  • Input compression alone does not reduce the number of LLM calls or prevent repeated work.
  • Result reuse creates value only when similarity, input changes, and result stability are judged safely.

A/B Test

Positioning A/B test

  • Variant A - Compression: "We compress repeated prompts to reduce token usage."
  • Variant B - Safe reuse: "We reduce repeated LLM calls by deciding when prior work can be reused safely."
  • Test criteria: compared buyer-pain clarity, business value, and follow-up discovery potential against the same cost/latency problem.
  • Result: selected Variant B because it connected the product to budget governance, workflow speed, and quality-risk control.

Loop

  1. Map: split repeated requests into task units.
  2. Score: judge task similarity, changed inputs, and result stability.
  3. Gate: reuse safe outputs through cache/RAG and block risky reuse.
  4. Sell: explain AI adoption value through cost control, reliability, and repeatability.
