CLOVA AiCall

AICC Ops Research

| CLOVA AiCall operations gaps and 3 action plans from public data

Overview

  • Period: 2026.05.12 - 2026.05.17
  • Team: Solo project
  • Analysis goal: Derive CLOVA AiCall adoption inquiry touchpoints and operations improvement points from competitor benchmarking and public Hugging Face support data.

Scope

  • Classified 29,872 public Hugging Face customer-support inquiries into 8 types.
  • Compared NAVER Cloud, KT, LGU+, SKT, and SK AX product pages, consultation forms, and metric disclosure.

Findings

Hugging Face public inquiry type analysis

  • High volume, low risk: Tasks 33.13%(9,896), billing 25.00%(7,468), account/auth 18.31%(5,469)
  • Low volume, high risk: Incidents/errors 4.73%(1,412), complaints 3.35%(1,000)
  • Low volume, low risk: Agent handoff 7.00%(2,092), FAQ/simple guidance 4.63%(1,384), other 3.85%(1,151)

AICC adoption-stage competitor comparison

  • Competitors: Surface diagnostic forms, pricing, and outcomes early.
  • NAVER: Detailed operations structure, but the adoption page is underused.

Proposal

Conclusion: Customers need clearer adoption information and in-operation metrics before choosing CLOVA AiCall.

  1. Clarify inquiries: Collect channel, volume, FAQs, and automation targets upfront.
  2. Package ops data: Report case volume, auto-response rate, and quality checks in customer terms.
  3. Structure risk inquiries: Classify incidents, errors, and complaints by self-service vs. expert-support level.

DeToks

LLM CLI Token Optimization Tool

Core role: Designed token-saving core logic and cache decision criteria

Overview

  • Period: 2026.04.20 - 2026.05.16
  • Team: 4-person team project
  • Contribution: Core logic direction, task decomposition, and cache decision criteria design

Problem

Core problem

  • LLM CLIs repeatedly inject the same context for recurring tasks, increasing token use and cost.
  • Input compression alone cannot reduce the number of LLM calls.
  • Result reuse requires criteria for judging whether tasks are the same.

Solution

Representative work

  • Designed core logic that splits requests into task units and reuses results.
  • Defined criteria for task similarity, input changes, and result stability.
  • Structured the Task Graph and RAG flow to show the token-saving effect.

Representative contribution

  • Identified edge cases in repeated, similar, and context-shifted requests.
  • Suggested validation perspectives to reduce incorrect cache reuse.

Impact

  • Strategic shift: Reframed input compression into an LLM call-minimization structure.
  • Core design: Organized task decomposition, result reuse, and cache criteria into a token-saving flow.
  • Quality refinement: Built criteria to reduce incorrect reuse through edge cases.
