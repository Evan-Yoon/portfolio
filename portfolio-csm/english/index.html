Role

  • Role: BDR-style use-case builder / solo project owner
  • Scope: Unity 6 robot arm demo, Asset Manager upload, Unity MCP workflow test

Customer

  • Target personas: product demo owners, training managers, robotics teams, and technical evaluators in industrial accounts.

BLIZZARD

Customer Signal Loop

Core role: Converted player friction into policy feedback and enablement content

Role

  • Role: Customer Service Agent / GM for World of Warcraft customer cases
  • Case scope: gameplay, account, refund, bug, event, government inquiry, and incident communication.
  • BDR relevance: handled rejection, policy constraints, emotional objections, and fast follow-up under live service pressure.

Objection

  • A repeated refund issue came from customers who paid on the wrong account and could not access that account within the standard window.
  • The policy answer alone was correct, but it did not resolve the customer’s real objection: the experience felt unfair and under-explained.
  • I held the refund principle, documented the recurring pattern, and proposed a customer-facing exception criterion tied to account access history.

Loop

Feedback loop

  1. Listen: identify the business reason behind angry tickets, not only the surface request.
  2. Classify: separate policy, UX, bug, and education issues.
  3. Document: turn repeated tickets into examples, judgment criteria, and response templates.
  4. Escalate: submit the pattern for internal review and standard procedure improvement.

Enablement loop

  • Created shared guidance that helped teammates handle repeated inquiries faster and more consistently.
  • Wrote 60+ Korean Wowhead guide comments to move repeated player questions toward self-service learning.

Impact

  • CSAT improved: customer satisfaction moved from 74% to 83% during my support period.
  • Process gain: peer feedback indicated the shared document reduced repeated case handling time to roughly one-third.
  • BDR fit: proved I can turn rejection and objection into clearer messaging, cleaner qualification, and better follow-up.

Core role: Cross functional communication for KPI-based operating changes

Role

  • Role: HR / General Affairs operator in Sales Support at Josun Palace and Josun Hotels & Resorts.
  • Stakeholders: department heads, vendors, HR solution companies, universities, employees, and managers.
  • BDR relevance: practiced cross functional communication while aligning business pain, data, and follow-up owners.

A/B Test

Channel and message experiment

  • Before: hiring relied heavily on standard job boards such as JobKorea and Saramin.
  • Test: expanded candidate touchpoints through LinkedIn, Jasoseol.com, SNS promotion, university contacts, and clearer role messaging.
  • Result: applicant inflow improved by more than 5x, and target opening fulfillment improved from 60% to around 98%.

Value

KPI-based value selling

  • When a call center and reservation vendor requested a fee increase, I reframed the conversation around call volume, answered calls, abandoned calls, and response-rate accountability.

Loop

  1. Discover: collect signals from new hires, managers, vendors, and operational data.
  2. Package: translate pain into retention, hiring, and service KPI language.
  3. Sell: present a measurable operating change to the right internal and external stakeholders.
  4. Improve: onboarding and follow-up interviews helped reduce turnover from 50% to 15%.

Role

  • Role: solo research owner for a customer-support automation market analysis.
  • Data: classified 29,872 public support inquiries into 8 issue types.

Segment

  • High-volume / low-risk: task requests, billing, account, and authentication issues that can support automation messaging.

Loop

  1. Research: use public data to define pain clusters before outreach.
  2. Message: tailor one outreach angle by persona and risk profile.
  3. Qualify: separate automation fit from quality-management fit.
  4. Handoff: route high-intent accounts to AE/AM with pain, metric, and next-step context.

WALKMATE

Problem Reframing

Core role: Repositioned an AI prototype around user journey value, not detection features

Role

  • Role: Team Lead / product strategist for a 3-person AI walking assistance PoC.
  • Contribution: problem redefinition, priority alignment, voice-first UI flow, and quality criteria.
  • Target users: visually impaired walkers and operators who need to review risk-detection evidence.

Problem

  • The first concept over-indexed on tactile paving obstacle detection and missed the full walking journey.
  • User value was clearer around destination movement, route recovery, and reduced interaction burden.
  • Without risk image, location, and detection-type records, false positives and delayed guidance would be hard to diagnose.

A/B Test

Value message test

  • Angle A: "AI detects obstacles on tactile paving."
  • Angle B: "AI helps users continue the walking journey and gives operators evidence for quality review."
  • Decision: used Angle B because it connected the product to user outcome, operator workflow, and supportability.

Loop

  1. Discover: reframe the real job-to-be-done from obstacle alerts to route confidence.
  2. Design: create a voice-first flow for risk detection, guidance, route recovery, and admin review.
  3. Measure: define guidance delay, route deviation, duplicate TTS, and detection record quality.
  4. Sell: explain the PoC as a safer journey and support loop, not just a computer-vision feature.

DeToks

AI Cost Story

Core role: Reframed an LLM tool as a business case for reducing repeated AI work

Role

  • Role: core logic planner for a 4-person LLM CLI token optimization project.
  • Contribution: task decomposition direction, cache decision criteria, and edge-case discovery.
  • BDR relevance: practiced translating technical architecture into cost, speed, and reliability trade-offs for AI buyers.

Problem

  • LLM CLI workflows repeatedly inject the same context, increasing token use, latency, and cost.
  • Input compression alone does not reduce the number of LLM calls or prevent repeated work.
  • Result reuse creates value only when similarity, input changes, and result stability are judged safely.

A/B Test

Value message test

  • Angle A: "We compress prompts to save tokens."
  • Angle B: "We reduce repeated LLM calls by deciding when prior work can be reused safely."
  • Decision: Angle B was stronger because it tied the product to budget governance, workflow speed, and quality risk.

Loop

  1. Map: split repeated requests into task units.
  2. Score: judge task similarity, changed inputs, and result stability.
  3. Gate: reuse safe outputs through cache/RAG and block risky reuse.
  4. Sell: explain AI adoption value through cost control, reliability, and repeatability.
